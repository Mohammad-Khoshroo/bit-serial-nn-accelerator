# معماری LLRT (لایه‌اجرای سطح‌پایین)

## ۱. نمای کلی
دایرکتوری `LLRT` (لایه‌اجرای سطح‌پایین) شامل پیاده‌سازی مرجع زبان C از لایه نرم‌افزاری است که بین مدل شبکه عصبی و شتاب‌دهنده سخت‌افزاری قرار می‌گیرد. وظایف اصلی آن عبارتند از:
۱. **کاشی‌کاری/زمان‌بندی (Tiling/Scheduling):** شکستن لایه‌های بزرگ (مثل Conv2d و Gemm) به قطعات کوچک‌تر که در محدودیت‌های سخت‌افزار (`I0` و `O0`) جا شوند.
۲. **مدیریت حافظه:** کپی کردن وزن‌ها، ورودی‌ها و بایاس‌ها در داخل BRAMهای نگاشت‌شده با AXI در سخت‌افزار.
۳. **کنترل سخت‌افزار:** پیکربندی رجیسترها، روشن کردن موتور (Start)، پایش (Polling) برای اتمام کار، و خواندن مجدد نتایج.
۴. **مدل مرجع طلایی (Golden Model):** ارائه پیاده‌سازی‌های کاملاً نرم‌افزاری لایه‌های کوانتیزه شده برای تأیید صحت سخت‌افزار.

*نکته: در این پروژه Cocotb، شما این کد C را کامپایل یا اجرا نمی‌کنید. شما باید آن را بخوانید و منطق دقیق آن (به‌ویژه در `driver.c` و `layer/*.c`) را به پایتون ترجمه کنید.*

## ۳. پیکربندی سخت‌افزار (`hardware_config.h`)
محدودیت‌های سخت‌گیرانه شتاب‌دهنده سخت‌افزاری را تعریف می‌کند.
```c
#define MAX_INPUT_SIZE 32 // که همان I0 است
#define MAX_NEURONS 32    // که همان O0 است
```
سخت‌افزار تنها می‌تواند در یک بار اجرا، ۳۲ ورودی و ۳۲ خروجی را پردازش کند. توابع لایه باید به این محدودیت‌ها احترام بگذارند.

## ۴. درایور سخت‌افزار (`driver/driver.c`)
این مهم‌ترین فایل برای کلاس `accel_driver` شما در Cocotb است. این فایل آرایه‌های نرم‌افزاری را به آدرس‌های AXI سخت‌افزار نگاشت (Map) می‌کند.

### چیدمان حافظه و آدرس‌های پایه
درایور از یک ساختار `acc_driver_t` استفاده می‌کند که شامل آدرس‌های پایه AXI است (که با مستندات سخت‌افزار مطابقت دارد):
*   `config_base_addr`: `0x40000000`
*   `iw_base_addr`: `0x40001000` (BRAM ورودی/وزن)
*   `o_base_addr`: `0x40002000` (بایاس/انباشتگرهای خروجی)

### تابع: `hw_setup`
این تابع داده‌ها را داخل BRAMها بارگذاری کرده و موتور را راه‌اندازی می‌کند.
```c
void hw_setup(uint8_t* input, int8_t* weight, int In_col, uint8_t input_zp, int i0, int o0) {
    // ۱. کپی کردن 'i0' ورودی در بلوک ۰ از آدرس iw_base_addr
    eaiot_hal_mem_copy(popenhw_driver.iw_base_addr, input, i0);

    // ۲. کپی کردن 'i0' وزن برای هر PE (به تعداد o0 بار) در بلوک‌های ۱ تا ۳۲
    // به ریاضیات آدرس‌دهی دقت کنید: I0 + oi * I0.
    // از آنجایی که I0=32 است، PE 0 آفست 32 می‌گیرد، PE 1 آفست 64 می‌گیرد و الی آخر.
    for (int oi = 0; oi < o0; oi++) {
        eaiot_hal_mem_copy(popenhw_driver.iw_base_addr + ((I0 + oi * I0)), weight + oi * In_col, i0);
    }

    // ۳. نوشتن output_num (یعنی o0-1) در آفست 0x04 کانفیگ
    int config_data = ((o0 - 1) & 0xFFFF);
    eaiot_hal_Out32(popenhw_driver.config_base_addr + 4 , config_data);

    // ۴. نوشتن start(1)، input_zp، و input_num (یعنی i0-1) در آفست 0x00 کانفیگ
    // بیت ۰: start=1، بیت‌های ۸-۱۵: input_zp، بیت‌های ۱۶-۳۱: i0-1
    config_data = ((input_zp & 0xFF) << 8) | (((i0 - 1) & 0xFFFF) << 16) | 1;
    eaiot_hal_Out32(popenhw_driver.config_base_addr, config_data);

    // ۵. پایش (Poll) آفست 0x04 کانفیگ، بیت ۱۶ برای مقدار 'done' (انجام‌شده)
    int done = 0;
    while(!done) {
        done = (eaiot_hal_In32((popenhw_driver.config_base_addr+4)) >> 16) & 0x1;
    }

    // ۶. پاک کردن بیت استارت با نوشتن ۰ در آفست 0x00 کانفیگ
    eaiot_hal_Out32(popenhw_driver.config_base_addr, 0);
}
```
*نکته برای پایتون: کد C به اندازه `i0` بایت (Byte) ارسال می‌کند. اما AXI به صورت ۳۲ بیتی است. در Cocotb، شما باید این مقادیر ۸ بیتی را در کلمات ۳۲ بیتی بسته‌بندی (Pack) کنید تا آن‌ها را روی پایانه AXI ارسال نمایید.*

### توابع: `bias_setup` و `recv_output`
```c
// کپی کردن 'o0' عدد صحیح ۳۲ بیتی در آدرس o_base_addr (0x40002000)
void bias_setup(int* bias, int o0) {
    eaiot_hal_mem_copy(popenhw_driver.o_base_addr, bias , o0 * sizeof(int));
}

// خواندن 'o0' عدد صحیح ۳۲ بیتی از آدرس o_base_addr (0x40002000)
void recv_output(int* out, int o0) {
    eaiot_hal_mem_copy(out, popenhw_driver.o_base_addr, o0 * sizeof(int));
}
```

## ۵. زمان‌بندی و کاشی‌کاری لایه‌ها (`layer/`)
از آنجا که سخت‌افزار تنها `I0=32` ورودی و `O0=32` خروجی را می‌پذیرد، توابع لایه، محاسبات را به حلقه‌های تو در تو تقسیم می‌کنند.

### مثال: `QGemm.c` (ضرب ماتریس‌ها)
```c
void QGemm(int* out, uint8_t* input, int8_t* weight, int* bias, ...) {
    for (int ir=0; ir < In_row; ir += 1) {
        for (int oc = 0; oc < Out_col; oc += O0) {         // کاشی‌کاری خروجی‌ها به اندازه ۳۲
            int o0 = LLRT_MIN(Out_col - oc, O0);
            
            bias_setup(bias + ir * Out_col + oc, o0);      // بارگذاری بایاس برای این کاشی
            
            for (int ic = 0; ic < In_col; ic += I0) {      // کاشی‌کاری ورودی‌ها به اندازه ۳۲
                int i0 = LLRT_MIN(I0, In_col - ic);
                
                // ارسال کاشی به سخت‌افزار
                hw_setup(input + ir * In_col + ic, 
                         weight + oc * In_col + ic, 
                         In_col, input_zp, i0, o0);
            }
            recv_output(out + ir * Out_col + oc, o0);      // خواندن خروجی برای این کاشی
        }
    }
}
```
*نکته برای پایتون: متد `layer_scheduler.forward()` شما در Cocotب باید دقیقاً این ساختار حلقه را برای `QuantLinear` (Gemm) و `QuantConv2d` تکرار کند.*

### پدگذاری (`Padding.c`)
قبل از عملیات کانولوشن، ورودی با مقدار `input_zp` (نه با صفر) پدگذاری می‌شود تا صحت کوانتیزاسیون حفظ شود.
```c
for (int i = 0; i < Hp * Wp * Cin; i++) padded[i] = input_zp;
// سپس ورودی اصلی در مرکز آرایه پدشده کپی می‌شود
```

## ۶. مدل مرجع طلایی (`tests/ref/`)
این فایل‌ها شامل پیاده‌سازی ریاضیِ خالص عملیات کوانتیزه شده هستند. آن‌ها هیچ تابع سخت‌افزاری را فراخوانی نمی‌کنند. خروجی مورد انتظار را تنها با استفاده از ریاضیات اعداد صحیح در زبان C محاسبه می‌کنند.

### فرمول ریاضی (یافت شده در `RQGemm.c`، `RQConv2d.c` و غیره)
```c
temp += (((int)input[...]) - (int)input_zp) * (int)weight[...];
```
این فرمول دقیقاً با سخت‌افزار مطابقت دارد: `(ورودی - نقطه-صفرِ ورودی) * وزن`. 
*نکته برای پایتون: فایل `lsqplus.py` در پایتورچ از قبل این ریاضیات را مدیریت می‌کند. شما از پایتورچ به عنوان مدل طلایی خود استفاده خواهید کرد، اما دانستن این فرمول برای رفع اشکالِ عدم تطابق‌ها (Mismatch) کمک‌کننده است.*

## ۷. تست‌کیس‌ها (`tests/cases/`)
فایل‌های تست (مثل `gemm.c`، `conv2d.c` و غیره) نشان می‌دهند که سیستم چگونه اعتبارسنجی می‌شود:
۱. تولید اعداد تصادفی برای `input` (uint8)، `weight` (int8)، و `bias` (int32).
۲. فراخوانی تابع سخت‌افزاری (مثلاً `QGemm`) که در سخت‌افزار می‌نویسد و `hw_out` را می‌خواند.
۳. فراخوانی تابع مرجع (مثلاً `RQGemm`) که `ref_out` را به صورت نرم‌افزاری محاسبه می‌کند.
۴. مقایسه آن‌ها: `check_mem(hw_out, ref_out, size)`.
